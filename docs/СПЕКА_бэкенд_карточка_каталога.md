# СПЕКА (бэкенд): поддержка новой карточки конструкции в каталоге

**Репозиторий:** `TransAcoustic/backend`, ветка `develop`
**Стек:** C# / .NET 8, EF Core 8 + Npgsql (PostgreSQL), MediatR, Mapster, MinIO
**Заказчик изменений:** фронтенд новой карточки каталога (макет утверждён
26.09.2026). Переделка фронтенда уже готова (`TransAcoustic/frontend`,
файлы в `Дизайн/devbin read/rework/`), бэкенд пока не трогали.

## Контекст

Новая карточка конструкции в каталоге (экран «Расчет» → выбор конструкции)
состоит из: шапки производителя (логотип, название, сайт, **описание**),
серой полосы с названием и кнопкой «оф. страница», слайдера изображений,
таблиц «Требования» и аккордеона **«Документы»** с категориями
(СЕРТИФИКАТЫ, ПРОТОКОЛЫ ИСПЫТАНИЙ, АЛЬБОМЫ, ТЕХНОЛОГИЧЕСКИЕ КАРТЫ,
МОНТАЖНЫЕ СХЕМЫ, ТЕХНИЧЕСКИЕ ЛИСТЫ, КАТАЛОГИ | БРОШЮРЫ, Другое).

Текущему API не хватает трёх вещей:

| # | Что нужно | Почему сейчас невозможно |
|---|---|---|
| 1 | **Описание производителя** (`Issuer.Description`) | В `IssuerDto` только `name`, `countries`, `logoUrl`, `webSite` — абзац с описанием показать нечем |
| 2 | **Категория документа** (`Attachment.Category`) | `fileUrls` — плоский список `{name, url}`; фронт вынужден угадывать категорию по ключевым словам в имени файла (эвристика), файлы «без слов» падают в «Другое» |
| 3 | **Оплачено ли размещение** (`Construction.IsPaidPlacement`) | Фронту неизвестно, оплачено ли брендовое размещение: без флага всем конструкциям показывается расширенная брендовая карточка |

Все три изменения обратно совместимы: все новые поля опциональны, старые
клиенты продолжают работать без изменений.

> **Дополнение 28.09.2026** (план коррекции размещений, P1): Изменение 3
> переработано — bool `IsPaidPlacement` заменён на nullable-дату
> `PaidPlacementUntil` (авто-деградация карточки по истечении срока,
> без модерации). Добавлены Изменение 4 (счётчики `PlacementInteraction`)
> и Изменение 5 (приоритет выдачи оплаченных, вариант «а» — внутри группы
> приоритета). **Изменения 3–5 реализованы 28.09.2026** в локальном клоне
> `TransAcoustic/backend`, ветка `feature/catalog-placement-backend`,
> коммит `a70cbe7` (см. реализационные пометки в тексте и раздел
> «Реализация» внизу). Изменения 1–2 согласованы, но пока не реализованы.

## Изменение 1. `Issuer.Description` (описание производителя)

### 1.1. Требования

- Новое **опциональное** текстовое поле `Description` у производителя:
  1–3 абзаца обычного текста (без форматирования), мультиязычность НЕ
  требуется (хранится одна строка, как и `Name`).
- Ограничение длины: **до 2000 символов**, `nullable`.
- Поле редактируется админом там же, где карточка производителя
  (существующие `POST /api/Issuer` и `PUT /api/Issuer`), и возвращается
  во всех выдачах производителя (by id, paginated).
- Системный производитель «Общий» (`IssuerConstants.CommonIssuer`,
  id `e555a6d4-6427-490b-b2d7-5a7a587d6092`) — `Description = null`.

### 1.2. Что менять (по слоям)

**Domain** — `src/Acoustics.Domain/Entities/Guidebooks/Issuer.cs`:

```csharp

    /// <summary>Краткое описание производителя для карточки каталога. Опционально.</summary>
    public string? Description { get; set; }
}
```

**EF-конфигурация** —
`src/Acoustics.Infrastructure/Database/EntityConfigurations/Guidebooks/IssuerConfig.cs`
(сейчас конфигурация по конвенции; добавить явно):

```csharp

```

**Миграция** (PostgreSQL). Создать стандартной командой EF из
`Acoustics.Infrastructure` (в проекте используется `AppDbContextFactory`):

```bash

```

Ожидаемая операция:

```sql

```

Данных для бэкфилла нет — колонка остаётся NULL у всех строк.

**Application**:

- `src/Acoustics.Application/Models/Dto/Guidebooks/IssuerDto.cs` —
  добавить `public string? Description { get; init; }` (Mapster смапит
  по имени автоматически, `ConfigureMapping` менять не нужно).
- `CreateIssuerUseCase.cs` — в команду `CreateIssuerCommand` добавить
  `public string? Description { get; init; }`; при создании

- `UpdateIssuerUseCase.cs` — в `UpdateIssuerCommand` добавить то же поле;

- Валидация длины (как в проекте — инлайн в use case, FluentValidation
  для issuer не используется):
  `if (request.Description?.Length > 2000) return Failure(Error.Validation("Описание производителя: не более 2000 символов"));`

**API** — `IssuerController` менять не нужно: `CreateIssuerCommand` /
`UpdateIssuerCommand` биндятся `[FromForm]`, новое поле приезжает из
multipart-формы автоматически; сериализация `IssuerDto` добавит
`description` в JSON.

### 1.3. Контракт после изменения

`GET /api/Issuer/{id}` →

```json
{
  "id": "…",
  "name": "ООО «Завод керамзитового гравия «ТермоКомфорт»»",
  "countries": [1],
  "logoUrl": "…",
  "webSite": "https://keramzit.by",

```

ключ `Description` (те же правила, что у `WebSite`: null/пусто = очистить).

### 1.4. Критерии приёмки

1. `GET /api/Issuer/{id}` возвращает `description` (null, если не задано).
2. Создание/обновление производителя с `Description` сохраняет и
   возвращает его; пустое значение очищает поле.
3. Строка длиннее 2000 символов → ошибка валидации, данные не меняются.
4. Все существующие запросы (справочник производителей, привязка к
   конструкциям) работают без изменений; существующие тесты зелёные.

## Изменение 2. `Attachment.Category` (категория документа)

### 2.1. Требования

- У каждого вложения (`ConstructionAdditionalInfo.FileUrls` — документы
  «Документы»; `ImageUrls` не трогаем) появляется обязательная категория.
- Категории фиксированы (8 значений, порядок = порядок секций аккордеона
  на макете):

| Код | Enum | Секция аккордеона (RU) |
|---|---|---|
| 0 | `Certificate` | СЕРТИФИКАТЫ |
| 1 | `TestProtocol` | ПРОТОКОЛЫ ИСПЫТАНИЙ |
| 2 | `Album` | АЛЬБОМЫ |
| 3 | `TechCard` | ТЕХНОЛОГИЧЕСКИЕ КАРТЫ |
| 4 | `InstallationScheme` | МОНТАЖНЫЕ СХЕМЫ |
| 5 | `TechSheet` | ТЕХНИЧЕСКИЕ ЛИСТЫ |
| 6 | `Catalog` | КАТАЛОГИ \| БРОШЮРЫ |
| 7 | `Other` | Другое (значение по умолчанию) |

- Категория задаётся при загрузке файлов (редактирование конструкции,
  «Документы»); по умолчанию — `Other`.
- В выдачах доп. информации (`GET` additional-info, вариант for-report)
  каждый элемент `fileUrls` несёт категорию.
- **Обратная совместимость:** существующие JSON-записи без поля
  `Category` при чтении дают `Other`; клиенты, не передающие категории
  при загрузке, получают `Other` для всех файлов. Ничего не ломается.

### 2.4. Критерии приёмки

4. Повторная загрузка «Документы» (полная замена списка, как сейчас)
   перезаписывает и категории.
5. Существующие тесты зелёные; для use case обновления файлов желателен
   юнит-тест на «категории короче списка файлов → недостающие = Other».

## Изменение 3. `Construction.PaidPlacementUntil` (оплаченное размещение, дата окончания)

> **Переработано 28.09.2026** (P1-2 плана коррекции размещений): bool
> `IsPaidPlacement` заменён на nullable-дату — карточка деградирует в
> базовую сама по истечении срока, без модерации. Бэкенд ещё не
> реализован, поэтому контракт правится на месте (миграции под bool не
> будет). Статус: черновик, согласовать с владельцем.

### 3.1. Требования

- Новое **опциональное** (nullable) поле-дата `PaidPlacementUntil` (UTC)
  у конструкции (ConstructionHeader): дата в будущем — размещение
  оплачено (расширенная брендовая карточка: шапка производителя,
  «оф. страница», слайдер, документы), `NULL` — не оплачено (базовая
  компактная карточка без брендинга).
- Управляется админом при редактировании конструкции (существующие
  `POST/PUT /api/Construction`): покупка/продление = установка новой
  даты окончания. Коммерческая семантика: платная услуга размещения.
- Возвращается в **детализации** (`GET /api/Construction/{id}`) и в
  **пагинированных списках** (`alternativeConstructions`, get-paginated),
  где карточки рендерятся фронтом.
- **Обратная совместимость:** поле отсутствует в ответе (старый бэкенд) →
  фронт считает `true` (брендовая карточка, как сейчас). Поле `null` от
  нового бэкенда → не оплачено. Бэкфилл: всем существующим конструкциям
  `PaidPlacementUntil = NULL`, затем проставить даты явно оплаченным
  (список — решение владельца; безопасный старт — все не оплачены).

### 3.2. Что менять (по слоям)

**Domain** — `src/Acoustics.Domain/Entities/Guidebooks/_Construction_/ConstructionHeader.cs`:

```csharp
/// <summary>Дата окончания оплаченного размещения (UTC). NULL — не оплачено.</summary>
public DateTime? PaidPlacementUntil { get; set; }
```

**EF/миграция** (PostgreSQL):

```sql
ALTER TABLE "ConstructionHeader" ADD "PaidPlacementUntil" timestamptz NULL;
```

```bash
dotnet ef migrations add AddCatalogPaidPlacement -p src/Acoustics.Infrastructure -s src/Acoustics.API --context AppDbContext
```

> Реализовано 28.09.2026 (ветка `feature/catalog-placement-backend`, коммит
> `a70cbe7`): одна общая миграция `AddCatalogPaidPlacement` на Изменения 3+4
> (колонка + таблица событий). Для design-time запуска dotnet-ef нужны
> фиктивные значения обязательных env-переменных (`DATABASE_*`, `MINIO_*`,
> `SMS_*` и др. — `SMS_PRIORITY` это bool) и пакет
> `Microsoft.EntityFrameworkCore.Design` в стартовом проекте (в репо не
> коммитился, ставится временно).

**Application**: включить поле в `ConstructionHeaderDto` /
`PaginatedConstructionHeaderDto` (Mapster смапит по имени); добавить в
команды create/update с валидацией «менять может только админ» (по
аналогии с существующими админ-ограничениями). Формат: UTC; прошедшая
дата допустима — она просто означает «не оплачено».

### 3.3. Контракт после изменения

`GET /api/Construction/{id}` и элементы `alternativeConstructions` /
`get-paginated`:

```json
{ "id": "…", "name": "…", "paidPlacementUntil": "2026-12-31T23:59:59Z", … }
```

`"paidPlacementUntil": null` — размещение не оплачено.

### 3.4. Критерии приёмки

1. `paidPlacementUntil` в будущем → расширенная брендовая карточка;
   `null` → базовая (без шапки производителя, «оф. страница», слайдера
   и документов).
2. Отсутствие поля в ответе (старый бэкенд) ≡ `true` — вид карточек
   не меняется.
3. **Авто-деградация:** по истечении даты карточка становится базовой
   без участия модерации (фронт сравнивает с текущим временем; фоновые
   джобы на сервере не нужны).
4. Фронт для неоплаченных не запрашивает `GET /api/Issuer/{id}` и
   `POST /api/Construction/additionalInfo` при показе карточки
   (−2 запроса на карточку).
5. Существующие тесты зелёные. Фронт-правка централизована в конвертерах
   (`constructions.converter.ts`, `report.converter.ts`):
   `isPaidPlacement = поле отсутствует ? true : paidPlacementUntil > now`;
   мок-сервер демо перевести с bool на даты.

## Изменение 4. Счётчики размещения `PlacementInteraction` (P1-1)

> Добавлено 28.09.2026 (P1-1 плана коррекции размещений). **Реализовано
> 28.09.2026** (коммит `a70cbe7`). Цель — производитель видит результат
> размещения (трафик/скачивания), админ — основания для пролонгации.

### 4.1. Требования

- Новый домен-объект `PlacementInteraction` — факт взаимодействия с
  карточкой: конструкция (`ConstructionHeaderId`), тип (`SiteClick` —
  клик по ссылке сайта в шапке или кнопке «оф. страница»;
  `DocumentDownload` — скачивание документа из аккордеона «Документы»),
  момент (`OccurredAtUtc`, ставит сервер), пользователь (`UserId`,
  nullable — когда авторизован), UTM-строка (`Utm`, nullable — вся
  query с `utm_*` для сверки с аналитикой сайта).
- **Запись события:** `POST /api/Placement/interaction`. Фронт шлёт
  fire-and-forget (`navigator.sendBeacon` / `fetch` с `keepalive`) при
  клике — **переход не ждёт и не блокируется ответом**.
- **Выдача:** `GET /api/Placement/stats?from&to` — агрегаты по
  конструкциям: клики, скачивания, уникальные пользователи. Доступ —
  админ. Опциональный фильтр `constructionHeaderId`.
- События append-only (не редактируются, не удаляются); объёмы малые,
  ретеншн не ограничиваем. Ежемесячный отчёт производителю — вне скоупа:
  ручной экспорт CSV из stats (см. «Вне скоупа»).

```csharp
    public PlacementInteractionType Type { get; set; }
    public DateTime OccurredAtUtc { get; set; }
    public Guid? UserId { get; set; }

    /// <summary>Полная UTM-query ссылки (utm_source=devbim&utm_medium=catalog&utm_content=…).</summary>

```

FK на `ConstructionHeader` — без навигационного свойства (не тянуть
агрегат); проверку существования конструкции делать в use case.

**EF** — конфигурация: таблица `PlacementInteraction`, индекс
(`ConstructionHeaderId`, `OccurredAtUtc`) — под выборку stats.
Миграция `AddPlacementInteraction`.

**Application**:

- `CreatePlacementInteractionUseCase` — команда
  `{ ConstructionHeaderId, Type, Utm }`; `OccurredAtUtc = DateTime.UtcNow`

`POST /api/Placement/interaction` — без авторизации (каталог доступен
гостям), `GET /api/Placement/stats` — админ-policy по аналогии с
существующими админ-эндпоинтами.

## Изменение 5. Приоритет выдачи оплаченных конструкций (P1-3)

> Добавлено 28.09.2026 (P1-3 плана коррекции размещений). **Реализован
> вариант (а)** (коммит `a70cbe7`): оплата поднимает конструкцию только
> внутри одной группы `priority`, не выше конструкций с большим
> приоритетом.

### 5.1. Требования

- В выдачах, где фронт рендерит карточки (`alternativeConstructions`,
  get-paginated), оплаченные конструкции (`PaidPlacementUntil` >UtcNow)
  поднимаются выше при прочих равных.
- **Открытый вопрос (решает владелец).** Текущий `priority` несёт
  бизнес-смысл (10 — лабораторные, 8 — расчётные, 5 — общие). Варианты:
  - **(а) сортировка внутри группы** (предложение по умолчанию, менее
    вмешивающееся): sort key `(priority DESC, isPaidActive DESC, …)` —
    оплата двигает карточку только среди конструкций с тем же `priority`;
  - **(б) буст `+N` к `priority`** у оплаченных (N=1?) — оплата может
    поднять конструкцию над расчётными; коммерчески сильнее, но меняет
    инженерную логику подбора.
- Контракт JSON не меняется — меняется только порядок элементов.

### 5.2. Что менять

- Use case пагинации конструкций и выборка `alternativeConstructions`:
  добавить в сортировку признак активности оплаты, считая его в SQL
  (`"PaidPlacementUntil" > now() at time zone 'utc'` / выражение EF
  `x.PaidPlacementUntil > DateTime.UtcNow`). Конкретные файлы — уточнить
  при реализации (после утверждения варианта (а)/(б)).

### 5.3. Контракт после изменения

Без изменений JSON — только порядок элементов выдачи.

### 5.4. Критерии приёмки

1. Вариант (а): оплаченная и неоплаченная конструкции с одинаковым
   `priority` — оплаченная выше; оплаченная с `priority` 5 НЕ поднимается
   выше неоплаченной с `priority` 8.
2. Порядок внутри групп сохраняет текущую сортировку.
3. Юнит-тест на сортировку; существующие тесты зелёные.
